# ПЛАН: мод Telegram для Android (клиент) + бэкенд-мозг на ПК

> Решение пользователя: интерфейс — МОД Telegram (кнопки прямо в приложении).
> Плюс требование: сохранять исчезающие / самоуничтожающиеся фото и видео.
> Этот документ описывает клиент (мод). Серверная часть (Ollama, архив, поиск,
> движок автоответа, веб) остаётся из docs/PLAN.md и работает как БЭКЕНД-МОЗГ.

## 0. Архитектура (две части)

1. КЛИЕНТ — мод Telegram на телефоне (Android):
   - нативный доступ ко ВСЕМ сообщениям, включая секретные чаты и
     исчезающие медиа (это может только настоящий клиент/форк);
   - кнопки в интерфейсе чата: «Автоответ: режим», «Архив чата», строка
     черновика над полем ввода;
   - локальное сохранение исчезающих/самоуничтожающихся медиа в наш архив;
   - выгрузка всего в бэкенд-мозг на ПК (на отдельный диск).
2. БЭКЕНД-МОЗГ — на ПК (RTX 5060), из docs/PLAN.md:
   - Ollama (локальная модель + доступ в интернет), архив SQLite+FTS5,
     media на второй диск (storage.data_dir), движок автоответа, веб-панель.
   - Телефон обращается к нему по локальной сети / VPN (Tailscale).

Почему так: тяжёлую модель гонит ПК (телефон слабее), а мод даёт то, чего
нет у userbot — секретные чаты и исчезающие медиа.

## 1. Честно о масштабе

Полный форк Telegram — большой проект (сборка, NDK, подпись APK, ре-базинг
под апдейты). НЕ пишем с нуля. Берём готовый открытый форк как БАЗУ и
допиливаем. Это ключевое решение для реалистичности.

## 2. База: на каком форке строим

Кандидаты (открытый код, GPLv2, часть нужных функций уже есть):
- exteraGram — плагины, сохранение удалённых и исчезающих медиа;
- Nekogram X — сохранение отзываемых сообщений, гибкие настройки;
- Owlgram — сохранение удалённых/исчезающих, снятие запрета скриншота.
Рекомендация: exteraGram (активная разработка + система плагинов, часть
нашей логики можно оформить плагином, меньше правок ядра).

Про лицензию: Telegram Android — GPLv2. Любой форк ОБЯЗАН оставаться
открытым, при распространении — публиковать исходники. Для личного
использования это не проблема.

## 3. Что добавляем поверх базы (наш объём работ)

A. UI в экране чата (наш «скин Nersiti»):
   - пилюля «Автоответ: off / draft / auto·preset / auto·generate /
     auto·dialogue» в шапке чата -> открывает настройки режима для чата;
   - иконка «Архив чата» в шапке -> экран полного локального архива чата
     (все сообщения, удалённые, изменённые, сохранённые исчезающие медиа);
   - панель черновика над полем ввода: показывает ответ модели,
     кнопки «Отправить» / «Изменить» (режим draft) либо авто-отправка (auto).

B. Локальный архив на телефоне (SQLite) — зеркало схемы из PLAN.md §5,
   плюс новые поля (см. §5 ниже). Хранит всё, что прошло через клиент.

C. Выгрузка (sync) в бэкенд-мозг на ПК — периодически/по событию шлёт
   новые сообщения и файлы на ПК (архив на отдельный диск). См. §6.

D. Сохранение исчезающих медиа (главная новая фича) — см. §4.

E. Связь с моделью — для генерации черновиков/ответов клиент обращается к
   бэкенду (Ollama на ПК). Ответ приходит в панель черновика.

## 4. Сохранение исчезающих / самоуничтожающихся медиа (по типам)

Общий принцип форка: клиент сам получает медиа в открытом виде на устройстве
пользователя, поэтому может сохранить его копию в наш архив.

1. «Просмотр один раз» / self-destruct в ОБЛАЧНЫХ чатах:
   - сохранить файл в наше хранилище в момент получения/открытия;
   - пометить в БД was_disappearing=1, self_destruct=1.
2. СЕКРЕТНЫЕ чаты (E2E, MTProto secret):
   - форк расшифровывает как обычный клиент -> сохраняем расшифрованные
     медиа и текст в наш архив; пометить is_secret=1.
   - (сторонние userbot-библиотеки это не умеют — поэтому нужен мод.)
3. Авто-удаление по таймеру (TTL) в облачных чатах:
   - архивируем сообщение/файл сразу при получении; помечаем ttl=1.
4. Отзыв (recall) собеседником:
   - сообщение/медиа уже в архиве; при удалении помечаем is_deleted=1,
     из архива не убираем.

Технически в базовых форках пункты 1, 2, 4 частично уже есть — наша задача
включить их, унифицировать и складывать в НАШ архив + выгружать на ПК.
Реализация — через хуки в местах, где ядро обрабатывает self-destruct
таймеры и расшифровку секретных чатов.

Замечание: это функции для СВОИХ полученных сообщений на СВОЁМ устройстве
(аналог скриншота). Собеседник может не знать, что копия сохранена, —
использовать ответственно и для личных нужд.

## 5. Изменения схемы архива (и на телефоне, и на ПК)

К таблицам из PLAN.md §5 добавить в messages и media поля:
- was_disappearing INTEGER DEFAULT 0   -- было исчезающим/one-time
- self_destruct    INTEGER DEFAULT 0   -- самоуничтожение по просмотру
- is_secret        INTEGER DEFAULT 0   -- из секретного (E2E) чата
- ttl              INTEGER DEFAULT 0   -- было авто-удаление по таймеру
- synced           INTEGER DEFAULT 0   -- выгружено на бэкенд-ПК (телефон)

В экране «Архив чата» такие сообщения помечать значком (напр. 🔥 «сохранено
исчезающее», 🔒 «секретный чат»).

## 6. Связь телефон <-> ПК (sync API на бэкенде)

Бэкенд (FastAPI из PLAN.md) добавляет защищённый API (только локальная
сеть / Tailscale, токен в заголовке):
- POST /sync/messages   — пачка новых сообщений (JSON) -> в архив ПК;
- POST /sync/media      — загрузка файла (multipart) -> в media на диске ПК;
- POST /ai/reply        — {chat_id, incoming_text, mode} -> текст ответа
                          (бэкенд зовёт ai.reply.make_reply / Ollama);
- GET  /health          — проверка доступности мозга.
Аутентификация: общий секрет (env SYNC_TOKEN), сверять на каждом запросе.
Если ПК недоступен — телефон копит в локальной очереди (synced=0) и шлёт
позже; черновики в оффлайне недоступны (модель на ПК).

## 7. Где считается модель

- Основной вариант: Ollama на ПК (RTX 5060). Телефон -> POST /ai/reply.
- Опция (позже): маленькая модель на телефоне (3B через MLC LLM /
  llama.cpp) для оффлайна — качество ниже, без интернет-инструментов.

## 8. Сборка и установка

- Android Studio, JDK 17, Android SDK + NDK.
- Свои api_id/api_hash (my.telegram.org) — вписать в конфиг сборки форка.
- Собрать APK, подписать своим ключом, поставить сайдлоадом на телефон.
- Обновления: периодически подтягивать upstream форка (rebase наших правок).

## 9. Риски

- GPLv2: код формально открытый.
- Правила Telegram: моды существуют, но агрессивная автоматизация (полный
  авто-ответ) повышает риск ограничений аккаунта. Дефолт — draft.
- Поддержка: каждый апдейт Telegram может ломать правки -> нужен ре-базинг.

## 10. Порядок реализации

1. Собрать выбранный форк «как есть», залогиниться, убедиться что работает.
2. Включить/проверить сохранение удалённых и исчезающих медиа (§4).
3. Добавить наш локальный архив-модуль (SQLite, схема §5).
4. Добавить sync-выгрузку на бэкенд-ПК (§6) + API на бэкенде.
5. Добавить кнопки в UI чата: автоответ, «Архив чата», панель черновика.
6. Связать черновики/авто-ответ с бэкендом (Ollama) (§3E, §6 /ai/reply).
7. Экран «Архив чата» на телефоне (значки исчезающих/секретных).
